# 18: Account deletion and archiving a Kid Profile

**What to build:** An adult permanently deletes their Account and all its data, and can archive a Kid Profile without losing its history.

**Blocked by:** 14 (Kid-Mode device).

**Status:** ready-for-agent

- [x] Deletion is confirmed with an email code. It hard-deletes every collection for the Account (ADR-0005), revokes all sessions including Kid sessions, and wipes local data on the device.
- [x] Archiving a Kid Profile hides it, keeps its history, and signs out its Kid-Mode devices.
- [x] Seam A test: after deletion, no record of the Account remains in any collection.

## Comments

Built on `ticket/18-account-deletion-and-kid-archive`:

- **Shared:** contract types `RequestDeletionCodeBody` (`language`) and `ConfirmDeletionBody` (`code`) in `account/deletion.ts`. Refusals reuse the sign-in reasons (`AuthErrorData`).
- **API, deletion (Seam A, `apps/api/test/accountDeletion.test.ts`):** `POST /account/deletion/code { language }` emails a 6-digit code (EN/AR template `email/accountDeletionCodeEmail.ts`, 10 minutes, resend after 60 s). `POST /account/deletion { code }` checks it (5 wrong guesses, counted before comparing, like sign-in) and calls `deleteAccountData` (`services/accountDeletion.service.ts`). Both are behind `requireAuth` + `requireFullScope`, so a Kid Session gets 403 `kid_session`. Deletion codes live in their own `AccountDeletionCode` collection (HMAC over `delete-account:<accountId>:<code>`), so a sign-in code never works as a deletion code and the other way round. `deleteAccountData` deletes Sessions first (every device, Kid-Mode ones included, is signed out at once), then **every Mongoose model with an `accountId` path**, found through `mongoose.modelNames()`, then the email's `SignInCode`, then the Account. A new collection with `accountId` is deleted with no code change.
- **The "nothing left" test** scans every collection in the database (`db.collections()`) for any document whose JSON mentions the Account's id or email. First it checks coverage: every registered model's collection must hold some of the Account's data before deletion (only `counters` is exempt, in `NOT_ACCOUNT_DATA`). A future model then fails the test until `wholeAccount()` fills it, so it can't be missed silently. Other tests: other Accounts untouched, all sessions and refresh tokens get 401, signing in again starts a new empty Account, wrong/expired/used-up/missing code, resend limit, validation, Kid Session refused.
- **API, archive (Seam A, `apps/api/test/kidArchive.test.ts`):** archiving is a normal `kidProfile` sync push with `archivedAt`. After a push is stored, `sync.service` checks each pushed Kid Profile's **stored** copy. If it's archived or deleted, `tokens.endKidSessions(accountId, kidProfileId)` deletes its Kid Sessions. An archive that lost to a later edit signs no one out. History stays and is still pulled by full sessions. Ticket 14's `/kid-devices` already refuses an archived kid, and setup works again after a restore. `endKidSessions` is the only new session helper (one `deleteMany`). Ticket 15's revocation can sit next to it.
- **Mobile data (Seam B):** `authSession.forget()` (forget the session and wipe without calling logout; `signOut` now uses it). `src/auth/accountDeletion.ts` `createAccountDeletion({ request, auth })` → `requestCode(language)` / `confirm(code)` returning `DeletionResult`; on success it calls `forget()`, so local records, unsynced changes and the PIN hash copy go and the status is `signedOut`. App singleton `accountDeletion` in `appSession.ts`. `kidWallet.ts`: `archiveKidProfile`, `restoreKidProfile`, `archivedKidProfilesQuery`. Tests: `src/sync/accountDeletion.seamB.test.ts` (wipe and sign-out, the tablet and Kid-Mode phone getting `needs_sign_in`, wrong code keeps everything, offline) and `src/sync/kidArchive.seamB.test.ts` (archived offline and hidden on both parent devices with wallet and history kept, restore, the archived kid's phone signed out but not the other kid's).
- **Screens:** Settings has a "Delete account" button (`danger` style: red on pale red, `app:delete`), hidden while the session needs a new code. To match the design's one red action, Sign out moved to `secondary`. `app/settings/delete-account.tsx` explains what is deleted (`app:gentle-warning` notice, "Signed in as" with `app:email`) and has "Email me a code". The code step uses the in-app keypad and code boxes, plus "Delete my account", a resend countdown and the sign-in error messages (offline has its own message). On success it goes to sign-in. The parent's kid wallet screen (`parent/kids/[id]`) has "Archive {name}" (`app:archive`, with a confirmation). An archived kid's wallet shows a notice, Full history and "Restore {name}" (`app:restore`), and hides Top up, Move money, Manage jars and the kid view. The Parent Area lists archived kids last ("Archived kids", with totals). Strings are under `settings.delete*` and `kidArchive.*`, in EN and AR.

**Left over / notes:**
- On a Kid-Mode phone that was signed out (kid archived, Account deleted or device revoked), the device still lands in `needsSignIn` with the wallet on screen. Ticket 15 owns "a revoked device is signed out on its next sync" on the device side. The archive and deletion cases should use the same handling, ideally wiping the device and showing sign-in.
- Other parent devices of a deleted Account also land in `needsSignIn` and keep their local copy until someone signs in. Signing in again creates a new Account ID, and `claimAccount` wipes the old data then. Wiping right away needs a "this Account no longer exists" reason from the server.
- A sync request that was already authenticated when deletion starts can still write after the data is deleted, leaving orphan records with no Account (the window is milliseconds). A second sweep, or checking the Account in `apply`, would close it.
- If the confirm response is lost after the server deleted the Account, the phone shows the offline error. The next request gets `session_ended` and shows sign-in-again, but the local data isn't wiped until a sign-in.
- Archived kids have no screen of their own. They reuse the wallet screen. The kid view and Learn rows are hidden for them.
