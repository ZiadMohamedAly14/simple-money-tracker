# 14: Kid-Mode device

**What to build:** A parent sets up their child's own phone. After setup the device shows only that child's wallet and Learn, and the device can't technically reach anything else.

**Blocked by:** 06 (Robust sync), 13 (Kid Expenses, Jar Transfers and history).

**Status:** resolved

- [x] Setup flow: sign in with an email code, choose "This device is for a kid", pick or create a Kid Profile, confirm the PIN. The device swaps to a Kid session and deletes the full tokens (ADR-0002).
- [x] The Kid session's scope covers one Kid Profile. Sync only returns that profile's records and only accepts Kid Expenses for it.
- [x] Seam A tests: a Kid session can't read Personal data, Top-ups, Jar Transfers or other kids, and can't write them.
- [x] A Seam B scenario: a Kid-Mode device only ever holds its Kid Profile's records.

## Comments

Built on `ticket/14-kid-mode-device`:

- **Shared:** contract types `StartKidSessionBody` (`kidProfileId`, `pin`, `deviceLabel?`), `KidSessionData` (`accessToken`, `refreshToken`, `kidProfileId`) and `KidSessionErrorData` (`kid/kidDevice.ts`).
- **API:** `POST /kid-devices` (`routes/kidDevice.routes.ts`, `services/kidDevice.service.ts`). It's behind `requireAuth` + `requireFullScope`, so a Kid Session gets 403 `kid_session`. It checks that the Kid Profile belongs to this Account and isn't deleted or archived (404 `kid_not_found`). Then it checks that a PIN exists (409 `no_pin`) and checks the PIN with 11's `checkPin` (now exposed on `ParentPinService`), so a wrong PIN gets the same throttle (403 `wrong_pin` / 429 `pin_locked`). Then it starts a Kid Session (`tokens.startKidSession`) and **deletes the full session the request came from**, so the full tokens stop working on the server, not only on the device. `AuthContext` gains `kidProfileId`. `authenticate` now reads the scope and Kid Profile from the stored Session, not the token claim. Refresh keeps the Kid scope.
- **Sync scope (`sync.service.ts`, closed rules table):** `kidReads` is a per-entity filter, or null for nothing. A Kid Session pulls `accountSettings` (for currency and digits, as 07 asked), its own `kidProfile`, its own `jar`s and its own `kidTransaction`s (all kinds, because balances and My history need Top-ups and Jar Transfers). It pulls no Categories, Month plans, Category Budgets, Transactions or other kids. `kidWrites` exists only on `kidTransaction`: `kind === 'kidExpense'` and its own `kidProfileId`. That rule is checked on the pushed record **and on any stored copy** (`checkKidScope`), so a kid can't take over a Top-up or Jar Transfer ID and edit or delete it as a "Kid Expense". `checkWallets` already makes the Jar belong to the same Kid Profile. Refusals are 403 `{ reason: 'kid_session' }`. A Kid Session doesn't create the Other Category.
- **Seam A (`apps/api/test/kidDevice.test.ts`, 16 tests):** setup swaps sessions (old access and refresh tokens get 401), refresh keeps the Kid scope, the wrong-PIN throttle, no PIN, wrong/archived/foreign Kid Profile, Kid Session can't set up another kid, validation. Reads: only its wallet plus settings, never Personal data or Lina, and later changes stay filtered. Writes: Kid Expense add/edit/delete reaches the parent. Refused: Top-ups and Jar Transfers (even its own), reusing a Top-up's or Jar Transfer's ID, another kid's expenses or Jars, Personal data, settings, Kid Profiles, Jars. Also refused: `/account/pin` and `/account/onboarding`.
- **Mobile data:** `StoredSession.kidProfileId` (SecureStore `auth.kidProfileId`). `authSession.becomeKidDevice` posts `/kid-devices`, replaces the full tokens with the Kid Session's, and calls `claimAccount(accountId, { kidProfileId })`. That call **wipes the local database** whenever the Device Mode or Kid Profile changes, so nothing the parent's full session downloaded stays. A Kid-Mode device gets no Other Category and its onboarding state is `complete`. `authSession.kidProfileId()` and the `useKidModeProfileId()` hook are new. `src/kid/kidDeviceSetup.ts` `setUpKidDevice` syncs first (so a kid created on this phone reaches the server), swaps, then syncs to download the wallet. The PIN hash copy is forgotten on becoming a Kid-Mode device (`forgetPinOnSignOutOrKidMode`, renamed from `forgetPinOnSignOut`), and `appPinGate` doesn't refresh it there (ADR-0002).
- **Seam B (`src/sync/kidDevice.seamB.test.ts`):** "only ever holds its Kid Profile's records". This covers after setup, after the parent changes Personal data and both wallets, and after an app restart. Also: offline Kid Expenses reaching the parent, the PIN hash copy and full access being gone (`GET /account/pin` 403), creating the kid on the kid's phone during setup, and a wrong PIN or being offline leaving the device a full device. `testDevice` gained `setUpKidDevice`, `kidProfileId`, `heldRecords`, `restartApp` and `request`.
- **Screens:** the Parent Area has "Set up this phone for a kid" (`app:kid-device`), which opens `parent/kid-device` ("Set up this device", PDF page 13). That screen has the "This device is for a kid" row, "Signed in as …" (`app:email`, the email in a direction isolate), the list of Kid Profiles, and "Create a new kid" (`parent/kids/new?next=kid-device` comes back with the new kid picked). Next opens `parent/kid-device/pin` ("Confirm your PIN", digits-only keypad, Finish), with wrong-PIN, locked countdown, offline and kid-not-found messages. The PIN is on its own step rather than inline as in the mockup, because the keypad needs the room. On a Kid-Mode device `/` redirects to `/kid/[id]`, which drops the back button, gains pull to refresh, and shows a "Getting your wallet…" state (`app:cloud`) until the first download lands. Its Learn row (`app:learn`) was already there from 13/16. The root layout sends any other top-level route (`useSegments` allow-list: index, `kid`, `learn`) back home on a Kid-Mode device. `Screen` takes an optional `refreshControl`. `email` is no longer in `RESERVED_APP_ICONS`. Strings are under `kidDevice.*` and `parentArea.setUpKidDevice`, in EN and AR.

**Left over / notes:**
- Reading of the checklist: "can't read … Top-ups, Jar Transfers" is taken as "can't *write* them". The spec says a Kid Session "can read that wallet", and the kid's balances and My history are built from them. It still can't read another kid's.
- The entry point is the Parent Area (sign in → the PIN gate → Set up this phone for a kid), not a step in onboarding. A brand-new Account goes through 12's kid onboarding first (it creates the kid and the PIN) and then uses the same button. A "This device is for a kid" choice on "Who is it for?" would need currency, kid and PIN in one path. Left out.
- Ticket 15: PIN elevation, the "Parent Area needs internet" screen, leaving Kid Mode, and listing/revoking devices. The `deviceLabel` is set to the kid's name for that list. The root layout's allow-list (`KID_MODE_ROUTES` in `app/_layout.tsx`) must let the Parent Area through after elevation. A revoked Kid Session currently lands in `needsSignIn` while the kid's wallet stays on screen.
- Ticket 18: archiving a Kid Profile should end its Kid Sessions (`Session.scope: 'kid', kidProfileId`). A Kid Session for a profile archived later keeps syncing until then.
- A Kid Expense still goes in the outbox if it's made between the pre-swap sync and the swap. It's dropped by the wipe. The window is a few hundred ms during Finish.
